# Нарезка и качество поиска (блок 5.4)

Продолжение RAG блока 5.3 (`SimpleDirectoryReader → нарезка → Qdrant → QueryEngine`, корпус
`data/rag-block-03`). Вместо интуиции — замеры. Golden dataset из 28 вопросов, три стратегии
нарезки в отдельных коллекциях Qdrant, метрики Hit Rate@5, MRR@10 и Recall@10, re-ranker и подбор
`chunk_size`, `overlap` и `top-K` по числам.

## Golden dataset

`tests/eval/retrieval_dataset.json` — 28 вопросов по корпусу из 10 файлов, написаны вручную по
текстам документов. У каждого вопроса:

- `question` — так, как спросил бы пользователь;
- `relevant_doc_ids` — 1–3 файла корпуса, где есть ответ (id документа — имя файла: `02_tariffs_and_payment.md`);
- `evidence` — части ответа дословно из документа (у части — варианты написания): «4 900 ₽», «код 410»,
  «оплата картой 1 час». По ним считаются строгие метрики (ниже);
- `type` и `answer` — сценарий и эталон для человека; метрики их не используют.

| Сценарий | Вопросов | Пример | Нужные документы |
|---|---:|---|---|
| `fact` — точечный факт | 12 | До какой даты будет работать API v1 и что потом вернут запросы к нему? | `04_api.md` |
| `paraphrase` — тот же факт другими словами | 5 | Не хочу, чтобы уведомления кабинета будили меня ночью. Можно их приглушить? (тихие часы) | `06_notifications.txt` |
| `comparison` — сравнение | 5 | Тариф «Команда»: сколько стоит, сколько в нём участников и какой лимит запросов к API? | 3 файла: тарифы, команда, API |
| `multi_step` — несколько шагов или файлов | 6 | Ночью не проходит оплата картой — как быстро ответит поддержка и куда писать? | регламент (PDF) и оплата картой |

Покрыты все форматы: Markdown, текст, DOCX (обмен с 1С, календарь), PDF (таблица сроков
поддержки). У 6 вопросов 2–3 нужных документа, всего частей ответа — 37. `10_houseplants.txt` не нужен ни одному вопросу:
это отвлекающий документ. Тест проверяет схему, что все файлы есть в корпусе и что каждая цитата
дословно есть в одном из нужных файлов и ни в каком другом.

## Метрики

Выдача поиска — список фрагментов. Фрагмент считается за свой документ (имя файла), поэтому три
фрагмента одного файла подряд — три позиции.

- **Hit Rate@5** — доля вопросов, у которых среди первых 5 фрагментов есть фрагмент нужного документа.
- **MRR@10** — среднее `1 / позиция` первого такого фрагмента среди первых 10 (нет — 0).
- **Recall@10** — доля нужных документов вопроса, фрагменты которых есть среди первых 10; в среднем
  по вопросам.

Это те же определения, что у `HitRate`, `MRR` и `Recall` из `llama_index.core.evaluation`, если
отдать им id документов первых k фрагментов. Тест сверяет обе реализации.

**Строгие метрики** — те же три формулы, но нужный фрагмент — тот, в тексте которого есть часть
ответа дословно (`evidence`; без учёта регистра и переносов строк). Зачем: на 10 файлах документный
уровень почти не различает стратегии. На 512 токенах корпус — около 30 фрагментов, по 3 на файл,
и фрагмент нужного файла среди первых пяти найдётся почти при любой нарезке. Даже подставные
эмбеддинги из триграмм символов в песочнице дают документный Hit Rate@5 = 1.000 у всех
конфигураций. Строгий уровень видит то, ради чего меняют нарезку: дошёл ли до модели сам ответ
целиком, или граница фрагмента его разрезала.

Цена контекста — **токенов в top-5**: сколько текста получила бы модель из первых пяти фрагментов.
Крупные фрагменты чаще «содержат ответ», но и стоят дороже. Поэтому длина фрагмента стоит в таблице
рядом с метриками.

**Скорость retrieval** — медиана и p95 по вопросам, по 3 замера на вопрос после прогрева. Вектор
вопроса считается заранее (у всех стратегий он одинаков), поэтому замеряется сам поиск: ретривер
LlamaIndex плюс Qdrant. У строк с re-ranker к этому добавляется время re-ranker на вопрос: скорость
одной пары «вопрос — фрагмент» × число кандидатов. Оценки пар кешируются, и прямой замер на
повторных парах занизил бы время.

Один вопрос — это 1/28 = 0.036 любой метрики. Разница меньше — шум.

## Стратегии

| Стратегия | Как режет | Параметры |
|---|---|---|
| `fixed` (baseline) | `TokenTextSplitter`: окна по `chunk_size` токенов с перекрытием, граница — ближайший пробел; предложения не учитываются | 512 / 64 |
| `recursive` | `SentenceSplitter(paragraph_separator="\n\n", chunking_tokenizer_fn=split_sentences_ru)`: абзацы → русские предложения → части предложений → слова, пока кусок не влезет; куски склеиваются во фрагменты с перекрытием. Аналог `RecursiveCharacterTextSplitter` из LangChain (`HierarchicalNodeParser` — другой подход, здесь не используется) | 512 / 64 |
| `semantic` | `SemanticSplitterNodeParser`: эмбеддинг каждого предложения с одним соседом с каждой стороны (`buffer_size=1`); граница — где косинусное расстояние до следующей группы выше 95-го перцентиля. Модель — та же `bge-m3`, что у индекса | `buffer_size=1`, `breakpoint_percentile_threshold=95`; размер не задаётся |

**Русские предложения.** `split_sentences_ru` — модель NLTK Punkt для русского (`punkt_tab/russian`).
Она лежит в данных NLTK внутри `llama-index-core`, поэтому ничего не скачивается. По умолчанию
сплиттеры LlamaIndex режут необученной моделью и принимают сокращения вроде «т. е.» за конец
предложения. У русской модели свои промахи: «в год.» и «в мес.» она тоже считает сокращениями.

**Заметка про `recursive`.** Заголовок Markdown (`## Смена тарифа`) — отдельный абзац, и при склейке
он может остаться в конце фрагмента, а текст раздела уйти в следующий. На корпусе так кончаются
11 фрагментов из 28 на 512 токенах и 28 из 58 на 256; тест это фиксирует. Вопросы FAQ-разделов совпадают с заголовками
дословно, поэтому такой «хвост» поднимает в выдаче фрагмент без ответа — это видно только в
строгих метриках.

Коллекции — `docs_fixed`, `docs_recursive`, `docs_semantic` (512/64) и для подбора параметров
`docs_<стратегия>_<chunk_size>_<overlap>` (у semantic — `docs_semantic_b<buffer>_p<перцентиль>`), в
том же Qdrant, с той же моделью эмбеддингов. В payload каждой точки — метка нарезки
(`recursive:512/64`). Повторный запуск подключается к готовой коллекции, если метка и число
фрагментов совпадают.

## Re-ranker

`app/services/reranker.py`: вход — вопрос и кандидаты из Qdrant (`Candidate`: текст, документ,
близость), выход — те же кандидаты, отсортированные по оценке re-ranker, первые `top_n`.

- **`BAAI/bge-reranker-v2-m3`** через `sentence-transformers.CrossEncoder` — основной вариант.
  Мультиязычный, на базе той же `bge-m3`, бесплатный и без сети после первого скачивания весов
  (~2,3 ГБ). Читает вопрос и фрагмент вместе (`max_length=512` токенов пары), поэтому точнее
  векторов, но на CPU — проход большой модели на каждую пару. Пакеты — `requirements-embeddings.txt`
  (тот же `sentence-transformers`, что для E5 в блоке 5.1).
- **Cohere `rerank-v3.5`** — `RERANK__PROVIDER=cohere` и ключ `RERANK__API_KEY`: быстро, но платно и
  нужен доступ к `api.cohere.com`.
- **Кеш оценок пар**: в памяти процесса, а с `RERANK__CACHE_ENABLED=true` — ещё и в SQLite
  (`var/rerank_cache.sqlite`). В эксперименте сначала переранжируются 20 кандидатов, и для top-10
  оценки уже есть.

Схема: из Qdrant берутся `top-K` кандидатов (10 или 20), re-ranker сортирует их, метрики считаются
по новому порядку. С `top-K = 10` re-ranker только переставляет кандидатов, Recall@10 не меняется.
С `top-K = 20` он может поднять в первую десятку фрагмент с 11–20 места.

## Результаты (Windows)

1.19.1 в Docker Desktop. Golden dataset — 28 вопросов, один вопрос = 0.036 любой метрики. Команда —
`python scripts/chunking_experiment.py --out var\chunking_experiment.md`; ниже — её таблицы.

### Разбор

1. **Документный уровень — у потолка.** У fixed и recursive Hit Rate@5, MRR@10 и Recall@10 — 1.000:
   на всех 28 вопросах первый же фрагмент — из нужного файла. У semantic MRR@10 0.982 — на одном
   вопросе первым оказался фрагмент другого файла. Это ожидаемо. В корпусе 10 файлов и 28
   фрагментов, top-10 — треть корпуса, а `bge-m3` на таком корпусе в выборе файла не ошибается.
   Требование задания «Hit Rate@5 ≥ 0.5» выполнено с запасом — 1.000.
2. **Строгий уровень различает стратегии, но только через MRR.** Фрагмент с ответом всегда среди
   первых пяти (строгий Hit Rate@5 и Recall@10 — 1.000). Разница — в том, первым ли он идёт:
   recursive 0.964, fixed 0.958, semantic 0.946. Это меньше одного вопроса. Отставание fixed на 0.006 —
   это, например, один вопрос, где фрагмент с ответом третий, а не второй. Отставание semantic на
   0.018 — например, один вопрос, где он второй, а не первый. По качеству поиска стратегии на этом
   корпусе равны.
3. **Заметно влияет только размер фрагмента.** На 256 токенах строгий MRR@10 — 0.905 против 0.964,
   это примерно 1,7 вопроса. Вероятная причина: мелкий фрагмент чаще отделён от заголовка-вопроса
   или содержит только часть ответа. Зато контекст вдвое меньше: 978 токенов в top-5 против 2003. Перекрытие 32 или 64
   на этом корпусе ни на что не влияет: числа совпадают в обеих парах.
4. **Re-ranker на 512 токенах ничего не меняет** (0.964 → 0.964): порядок и так у потолка. На 256
   токенах он поднимает строгий MRR@10 с 0.905 до 0.946 (+1,1 вопроса), но это всё ещё ниже, чем
   512 без re-ranker. Цена на CPU — около 0,4 с на пару «вопрос — фрагмент»: ~4 с на вопрос при
   10 кандидатах и ~8 с при 20. Первый замер, 11 и 22 с, завышен скачиванием и загрузкой модели.
   Поиск при этом — 7 мс, то есть re-ranker в 500–1 000 раз дольше и заметно добавляет к ответу
   самой `llama3.2` (22–55 с в блоке 5.3). 20 кандидатов вместо 10 метрик не меняют: нужное и
   так в первой десятке.
5. **Скорость поиска одинакова** — медиана 7 мс у всех конфигураций: Qdrant на 28–58 точках ищет
   перебором. p95 около 30 мс — разброс Docker Desktop и WSL на Windows, а не стратегий.
6. **semantic** даёт самые неровные фрагменты (до 1 019 токенов: граница только по смыслу, размер не
   ограничен) и самую долгую индексацию (87 с). При этом MRR у неё чуть ниже остальных.
7. **Заголовки в конце фрагментов у recursive** (11 из 28 фрагментов) на этом наборе вопросов вреда
   не показали: строгий Hit Rate@5 — 1.000.

### Итог

**Выбираю стратегию recursive с конфигом chunk_size = 512, overlap = 64, top-K = 10, без re-ranker,
потому что:**

- по документным метрикам все три стратегии на потолке (Hit Rate@5 = 1.000), а по строгим recursive
  лучшая: MRR@10 0.964 против 0.958 у fixed и 0.946 у semantic. Разница в пределах одного вопроса,
  поэтому решают остальные свойства;
- при равном качестве у recursive цельные фрагменты по предложениям. fixed режет посреди фразы, а
  в блоке 5.3 версия без фреймворка с рваными фрагментами ответила на вопрос о лимитах API неполно.
  Размер ограничен 512 токенами, а у semantic доходит до 1 019. Индексация — 20 с против 87 у
  semantic;
- 256 токенов хуже примерно на два вопроса (MRR@10 0.905), и re-ranker это не компенсирует (0.946);
  overlap 32 и 64 не различаются — оставлен 64;
- re-ranker на 512 токенах ничего не добавляет, а стоит ~4–8 с на вопрос на CPU. 20 кандидатов
  вместо 10 метрик не меняют, а время re-ranker удваивают.

Финальный Hit Rate@5 — 1.000. Конфигурация совпадает со значениями по умолчанию в `RagSettings`
(`app/core/config.py`) и в `.env.example`: `RAG__CHUNKING=recursive`, `RAG__CHUNK_SIZE=512`,
`RAG__CHUNK_OVERLAP=64`, `RAG__CANDIDATES_TOP_K=10`, `RERANK__ENABLED=false`. Коллекцию сервиса
`rag_block_03`, собранную в блоке 5.3 без метки нарезки, нужно пересобрать один раз:
`python -m app.services.rag --rebuild` — получится 28 фрагментов.

### Ограничения и следующая итерация

На этом корпусе метрики у потолка, и разница между конфигурациями — один-два вопроса. Чтобы
следующие решения о нарезке опирались на надёжные числа:

1. **Усложнить golden dataset до 50+ вопросов.** Нужны вопросы, где ответ — одно предложение
   посреди длинного раздела; перефразы без общих слов с документом; вопросы, на которые похожие
   разделы есть в разных файлах (тарифы — в `02`, `04` и `07`).
2. **Взять корпус больше**, где top-10 — малая доля фрагментов: например, 110 статей базы знаний
   блока 5.2 отдельными документами или длинные регламенты в PDF.
3. **Гибридный поиск** (sparse + dense, Query API Qdrant) — для кодов ошибок и названий тарифов,
   где точное слово важнее смысла.
4. **Привязать заголовки Markdown к тексту раздела** (`MarkdownNodeParser` или склейка заголовка со
   следующим абзацем) и замерить это на усложнённом наборе.
5. **Re-ranker вернуть в рассмотрение** на большем корпусе, на GPU или через Cohere `rerank-v3.5`.
   Тогда цена — доли секунды, а не секунды.

### Песочница

**Песочница** проверяет только механику. Ollama и Hugging Face там недоступны: эмбеддинги —
подставной сервер (триграммы символов), re-ranker — подставной Cohere на том же принципе.
Результат: три коллекции стратегий и три — подбора проиндексированы, повторный запуск
подключается к готовым. Документный Hit Rate@5 — 1.000 у всех конфигураций, строгий MRR@10 различает их
(0.81–0.91). Время поиска — 5–9 мс. Таблицы и итоговые строки `.env` формируются; по этим числам
ничего не выбирается.

## Запуск

```powershell
pip install -r requirements-embeddings.txt          # sentence-transformers для bge-reranker-v2-m3
docker compose up -d qdrant
python scripts/chunking_experiment.py --out var\chunking_experiment.md --json var\chunking_experiment.json
python scripts/chunking_experiment.py --no-rerank       # без re-ranker: быстро, re-ranker на CPU — самая долгая часть
python scripts/chunking_experiment.py --rebuild         # переиндексировать коллекции эксперимента
```

Первый запуск скачивает веса re-ranker (~2,3 ГБ, `%USERPROFILE%\.cache\huggingface`). Если сеть
подменяет HTTPS-сертификаты — `LLM__USE_SYSTEM_CERTS=true`, как для моделей E5 в блоке 5.1. Порядок
работы: три стратегии; re-ranker на лучшей (20 и 10 кандидатов); подбор параметров — 4 нарезки × top-K
10/20, с re-ranker и без. `--no-sweep-rerank` оставляет re-ranker только на лучшей стратегии.

## Как это включено в сервис

- `RAGService` режет корпус стратегией `RAG__CHUNKING` с `RAG__CHUNK_SIZE` / `RAG__CHUNK_OVERLAP`
  (у semantic — `RAG__SEMANTIC_BUFFER_SIZE` / `RAG__SEMANTIC_BREAKPOINT`). Метка нарезки — в payload.
  Если коллекция нарезана иначе, это не ошибка: поиск работает, а в лог пишется
  `rag_chunking_mismatch`, CLI подсказывает `python -m app.services.rag --rebuild`.
- `RERANK__ENABLED=true`: из Qdrant берутся `RAG__CANDIDATES_TOP_K` кандидатов, re-ranker
  пересортировывает их, модели уходят первые `RAG__SIMILARITY_TOP_K`. Порог «не знаю» по-прежнему
  сравнивается с близостью из Qdrant, `score` в `sources` — тоже она. Re-ranker недоступен —
  `503 rerank_unavailable`.
- В Docker-образе `sentence-transformers` нет (сотни мегабайт torch и ~2,3 ГБ памяти на модель при
  пределе WSL 1,7 ГБ), поэтому `RERANK__ENABLED` по умолчанию выключен.
