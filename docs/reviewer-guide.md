# Инструкция для проверяющего: развёртывание и проверка в браузере

Как поднять проект на своём компьютере и проверить его через веб-интерфейс http://localhost:8000/ui.
Всё, что умеет ассистент, проверяется в одной вкладке браузера:
- **«Вопросы по документам»** — ответы по базе знаний со ссылками на источники и честный отказ;
- **«Поручение агенту»** — агент с подтверждением перед отправкой сообщения, пауза переживает
  перезапуск сервиса;
- **«Пополнить базу»** — загрузка нового документа и вопрос по нему.

Сколько времени нужно: установка — 30–60 минут (большую часть занимает загрузка моделей и образов),
проверка — 20–30 минут.

Сроки ниже измерены на ноутбуке автора: Ryzen 5 7530U, 16 ГБ памяти, без видеокарты, Windows, Docker
Desktop, модели в Ollama на процессоре. С видеокартой ответы будут быстрее.

## Веб-интерфейс и Telegram-бот

Пользоваться AI-ассистентом можно двумя способами: через веб-интерфейс http://localhost:8000/ui и через
Telegram-бота. Это два интерфейса одного сервиса:
- **Бэкенд общий.** Оба клиента обращаются к одному API (`POST /chats/{id}/messages`), а за ним стоят одна
  база знаний в Qdrant, те же модели в Ollama, тот же порог близости и одна база Postgres. На одинаковый
  вопрос в начале диалога они дают по существу одинаковый ответ с теми же источниками. Документ,
  добавленный через страницу, бот находит сразу.
- **Интерфейс разный.** На странице ответ растёт по словам, а источники показаны справа со шкалой
  близости. В боте ответ растёт правками сообщения, а источники идут списком под ним.
- **Диалоги независимы.** У каждого клиента свой чат и своя история. Вопрос, заданный боту, на странице не
  появится, и наоборот. Уточнение вроде «А при оплате по счёту?» опирается только на историю своего канала.

Поэтому диалог во вкладке «Вопросы по документам» — аналог разговора с ассистентом в Telegram: тот же
ассистент, другой интерфейс и своя история.

| Возможность | Веб-интерфейс `/ui` | Telegram-бот |
|---|---|---|
| Вопрос по документам, уточнение в диалоге, отказ вне базы | вкладка «Вопросы по документам» | любое сообщение боту или `/ask` с выбором раздела |
| Файл в чате | 📎: PDF, DOCX, фото | PDF, DOCX, фото, голосовое (голос — при ключе OpenAI) |
| Оценка ответа | 👍/👎 под ответом | 👍/👎 под ответом |
| Начать диалог заново | «Начать новый диалог» | `/clear` |
| Поручение агенту с подтверждением отправки | вкладка «Поручение агенту» | нет: агент работает в веб-интерфейсе, в консоли (`scripts/agent_cli.py`) и через API |
| Пополнение базы знаний | вкладка «Пополнить базу» | нет: в веб-интерфейсе и через API |
| Статистика, пользователи, рассылки | нет | `/stats`, `/users`, `/broadcast` — для администраторов из `BOT_ADMIN_IDS` |

Сообщение, которое агент «отправляет» в Telegram-чат после подтверждения, в бота не приходит. Отправка —
заглушка: она только пишет строку в лог сервиса.

Эта инструкция проверяет ассистента через веб-интерфейс — для него не нужно ничего, кроме браузера. Для бота
нужен свой токен от @BotFather в `BOT_TOKEN`; как сверить оба канала, описано в разделе 7.14. Голосовые
вопросы требуют ключа OpenAI и описаны в [`demo.md`](demo.md).

## 1. Что нужно на компьютере

| Что | Зачем | Проверка |
|---|---|---|
| Docker Desktop (Windows, macOS) или Docker Engine с Compose v2 (Linux) | весь стек: app, migrate, bot, redis, postgres, qdrant, phoenix | `docker compose version` |
| Ollama | языковые модели и модель эмбеддингов работают на хосте | `ollama --version` |
| Git | получить проект | `git --version` |
| Браузер | веб-интерфейс; проверен в Chrome и Яндекс Браузере | — |
| Python 3.12+ | только для необязательных проверок: `preflight.py` и автотестов (раздел 9) | `python --version` |

Память и диск:
- **Память — от 16 ГБ.** Три модели Ollama занимают около 6 ГБ, стек Docker — около 1,5 ГБ. Перед
  проверкой закройте тяжёлые программы.
- **Диск — не меньше 15 ГБ свободного места.** Модели — около 6 ГБ, образы Docker — ещё несколько ГБ.

Команды ниже — для Windows PowerShell из корня проекта. Где команды для macOS и Linux отличаются, они
приведены отдельно.

## 2. Получить проект

```powershell
git clone https://github.com/AlexBuQA/multapi.git
cd multapi
```

## 3. Загрузить модели Ollama

```powershell
ollama pull llama3.2              # ответы по базе знаний (3B)
ollama pull qwen3:4b-instruct     # агент: вызывает инструменты
ollama pull bge-m3                # эмбеддинги для поиска
```

Модели займут около 6 ГБ. `gemma3:4b` нужна только для вопросов по фото — в этой инструкции её нет.

Сервис в контейнере обращается к Ollama на хосте по адресу `host.docker.internal:11434`:
- **Windows и macOS:** настраивать ничего не нужно.
- **Linux:** Ollama по умолчанию слушает только `127.0.0.1`, и контейнер её не увидит. Задайте Ollama
  переменную `OLLAMA_HOST=0.0.0.0` (для службы systemd — `sudo systemctl edit ollama`, строка
  `Environment="OLLAMA_HOST=0.0.0.0"`) и перезапустите Ollama.

**По желанию — модели не выгружаются из памяти.** По умолчанию Ollama выгружает модель после 5 минут
простоя. Следующий ответ тогда ждёт её повторной загрузки: у автора вопрос после перерыва занял 139 с
вместо обычных 20–40. Чтобы модели держались час:

```powershell
setx OLLAMA_KEEP_ALIVE 1h         # затем закройте Ollama (значок в трее → Quit) и запустите снова
```

На macOS — `launchctl setenv OLLAMA_KEEP_ALIVE 1h` и перезапуск приложения Ollama, на Linux — строка
`Environment="OLLAMA_KEEP_ALIVE=1h"` там же, где `OLLAMA_HOST`.

## 4. Заполнить `.env`

```powershell
Copy-Item .env.example .env       # macOS, Linux: cp .env.example .env
notepad .env                      # или любой редактор
```

Впишите значения из таблицы. Остальные переменные оставьте пустыми — сервис возьмёт значения по
умолчанию. `.env` остаётся только на вашем компьютере: он в `.gitignore`.

| Переменная | Значение | Зачем |
|---|---|---|
| `LLM__OPENAI_API_KEY` | `ollama` | без ключа сервис не стартует; Ollama принимает любое непустое значение |
| `LLM__BASE_URL` | `http://localhost:11434/v1` | адрес Ollama для скриптов на хосте; контейнеру его задаёт `compose.yaml` |
| `LLM__DEFAULT_MODEL` | `llama3.2` | модель ответов по базе |
| `LLM__REQUEST_TIMEOUT` | `120` | секунд на ответ модели: на процессоре 30 по умолчанию мало |
| `AGENT__MODEL` | `qwen3:4b-instruct` | модель агента |
| `QDRANT_API_KEY` | сгенерировать | ключ векторной базы; без него `docker compose` не запустится |
| `ADMIN_TOKEN` | сгенерировать, не короче 16 символов | ключ администратора: агент и пополнение базы |
| `INTERNAL_TOKEN` | сгенерировать, не короче 16 символов | общий секрет сервиса и бота |
| `BOT_TOKEN` | по желанию | без него контейнер `bot` перезапускается с ошибкой — веб-интерфейсу это не мешает |

Сгенерировать значение — по одному разу для каждого из трёх ключей:

```powershell
[guid]::NewGuid().ToString("N")   # 32 символа; macOS, Linux: openssl rand -hex 24
```

## 5. Запустить стек

```powershell
docker compose up -d --build
docker compose ps
```

Что происходит:
1. Первая сборка занимает 5–15 минут: скачиваются базовые образы и зависимости Python.
2. Поднимаются семь контейнеров. `migrate` создаёт таблицы в Postgres и завершается — `Exited (0)` у
   него норма.
3. `app` становится `(healthy)` примерно через минуту.
4. При первом старте `app` в фоне индексирует корпус — 66 документов, 102 фрагмента в Qdrant. Это ещё
   около минуты на процессоре. Готово, когда в логе есть строка `ingest_done`:

```powershell
docker compose logs app | Select-String ingest_done    # macOS, Linux: docker compose logs app | grep ingest_done
```

Ожидаемый `docker compose ps`: `app`, `postgres`, `qdrant`, `redis`, `phoenix` — `Up … (healthy)`. `bot`
— `Up` при заданном `BOT_TOKEN`, иначе перезапускается.

**По желанию — проверка стенда одной командой** (нужен Python, раздел 9):

```powershell
python scripts/preflight.py --ask   # Ollama и модели, контейнеры, индекс Qdrant, тестовый вопрос
```

Ожидаемый итог — `Стенд готов: критичных проблем — 0`.

## 6. Открыть страницу и ввести ключ администратора

1. Откройте http://localhost:8000/ui. В шапке — зелёная точка «сервис работает», ниже три вкладки.
2. Скопируйте ключ администратора в буфер обмена, не выводя его на экран:

```powershell
(Select-String -Path .env -Pattern '^ADMIN_TOKEN=\s*"?([^"#\s]+)').Matches[0].Groups[1].Value | Set-Clipboard
```

   macOS: `sed -nE 's/^ADMIN_TOKEN=[[:space:]]*"?([^"#[:space:]]+).*/\1/p' .env | pbcopy`; Linux — та
   же команда с `xclip -selection clipboard` вместо `pbcopy`.

3. Нажмите «Ключ администратора: не задан» вверху справа → Ctrl+V → Enter. Кнопка станет «Ключ
   администратора: задан».

Ключ нужен вкладкам «Поручение агенту» и «Пополнить базу» — как заголовок `X-Admin-Token` в API.
Страница хранит его только до закрытия вкладки и нигде не показывает. Вопросы по документам работают без
ключа.

## 7. Сценарий проверки

Сроки — на ноутбуке автора:
- **Первый ответ после запуска стека — до 90 с:** модель загружается в память.
- **Обычный ответ по базе — 20–40 с.**
- **Ответ по файлу — 30–40 с.**
- **Агент до паузы — 1,5–2 минуты.**

Пока модель думает, под вопросом идёт счётчик: «Ищу в документах · N с» или «Читаю файл · N с», затем
«Пишу ответ». Формулировки ответов модели от запуска к запуску могут немного отличаться, а факты и
источники — нет.

### 7.1. Вопрос по базе с источниками

Вкладка «Вопросы по документам».

1. Нажмите пример «Сколько действует ссылка для сброса пароля?».
2. Ответ: «Ссылка для сброса пароля действует 30 минут.» и «Источники: [1]». Под ответом — «Ответ за
   N с», «источников: 5» и кнопки 👍/👎.
3. Справа «Источники ответа». Первым идёт `[1] password-reset.html` с отметкой «в ответе»:
   - путь `account/password-reset.html · account`;
   - шкала «близость 0.75» с янтарной отметкой «порог 0.50»;
   - начало фрагмента: «Восстановление (сброс) пароля…».

   Ниже — остальные найденные фрагменты (`delete-account.html` с близостью 0.60 и другие). Модель их
   нашла, но в ответе не цитировала.
4. Нажмите `[1]` в тексте ответа — источник справа подсветится.

**Что это показывает:** ответ строится только по найденным фрагментам, и каждый можно проверить по
источнику.

### 7.2. Уточнение в диалоге (по желанию)

1. «Каков срок возврата оплаты?» → 14 дней после списания.
2. «А при оплате по счёту?» → деньги возвращаются на расчётный счёт плательщика.

Второй вопрос неполный: сервис сначала переписывает его с учётом истории диалога и только потом ищет.
Поэтому ответ на него — на 20–30 с дольше.

### 7.3. Вопрос, ответа на который в базе нет

1. Нажмите «Начать новый диалог»: так отказ придёт без лишнего шага с переписыванием вопроса.
2. Нажмите пример «Как приготовить борщ?».
3. Ответ: «По базе не нашёл, могу эскалировать.», под ним — «ответа в документах нет».
4. Справа — янтарный блок «В документах ответа нет: лучшее совпадение ниже порога — модель ответ не
   писала, отказ без генерации». Серая шкала: близость 0.33 при пороге 0.50. Первым вопросом
   диалога отказ приходит за несколько секунд.
5. Спросите «Можно ли оплатить тариф криптовалютой?».
   - Ответ — тот же отказ.
   - Справа — «Похожие фрагменты нашлись, но ответа в них нет — модель отказалась сама, а не стала
     выдумывать».
   - Близость около 0.66, выше порога: модель вызывалась и отказала по правилу промпта.

**Что это показывает:** два слоя защиты от выдуманных ответов — порог близости и правило промпта.

### 7.4. Оценка ответа

Нажмите 👍 или 👎 под любым ответом. Ожидаемо: «оценка сохранена», кнопки становятся неактивными.
Оценка сохраняется в Postgres вместе с источниками.

### 7.5. Файл в чате

1. Нажмите 📎 и выберите `samples/support_rules.pdf` из папки проекта. Под полем появится «Приложен файл:
   support_rules.pdf. Без вопроса ассистент перескажет документ.».
2. Введите «Какие сроки ответа поддержки?» и нажмите «Спросить».
3. Ответ — список по приоритетам заявок: критический — 15 минут, высокий — 1 час, средний — 4 часа,
   низкий — 1 рабочий день. Справа: «Ответ по присланному файлу «support_rules.pdf»: база знаний для
   него не нужна.».

Модель на 3 млрд параметров может добавить в такой список неточные детали. Это известное ограничение,
оно описано в [`decisions.md`](decisions.md), раздел 10.

### 7.6. Агент: поиск, черновик, пауза перед отправкой

Вкладка «Поручение агенту». Ключ администратора должен быть задан (раздел 6).

1. Поручение уже вписано: «Найди в базе знаний, за сколько дней до окончания периода приходит письмо об
   автопродлении, и отправь клиенту в Telegram-чат 12345 короткое напоминание об этом.». В поле
   «Поручение» — его идентификатор вида `web-ГГГГММДД-ЧЧММСС`.
2. Нажмите «Выполнить». Справа от кнопок — «Агент работает · м:сс». Шаги появляются по мере работы:

| № | Шаг | Что в нём |
|---|---|---|
| 1 | Поручение принято | «Поручение web-…, роль write-with-approve.» |
| 2 | Агент вызывает инструмент | `search_knowledge_base(query="за сколько дней до окончания периода приходит письмо об автопродлении")` |
| 3 | Инструмент вернул результат · search_knowledge_base | `[billing/auto-renewal.docx, близость 0.71] Автопродление тарифа … за 3 дня до окончания периода приходит письмо…` |
| 4 | Агент вызывает инструмент | `send_telegram_message(text="Вы получите письмо об автопродлении за 3 дня до окончания периода.", chat_id="12345")` |
| 5 | Черновик сообщения готов | «Отправка ждёт вашего решения.» |
| 6 | Отправить это сообщение клиенту? | янтарная карточка: «Получатель: Telegram-чат 12345», текст сообщения, кнопки «Отправить» и «Отклонить» |

3. Справа «Состояние поручения»: «Ждёт решения — да», «Отправлено — нет», «Контрольная точка» — её
   идентификатор.

**Что это показывает:** агент сам выбрал инструменты, а отправку сообщения граф остановил до решения
человека.

### 7.7. Пауза переживает перезапуск сервиса

1. Кнопки карточки не нажимайте. В терминале выполните:

```powershell
docker compose restart app        # или Restart у контейнера multapi-app-1 в Docker Desktop
```

2. Сразу нажмите на странице «Обновить состояние». Ожидаемо: «Сервис не отвечает — жду, пока он
   поднимется…».
3. Через 20–60 с появится шаг «Состояние восстановлено из Postgres» с текстом «Контрольная точка …:
   агент по-прежнему ждёт решения». Под ним — новая карточка с тем же текстом сообщения. Прежняя
   карточка становится серой с пометкой «Решение — в восстановленной карточке ниже.».

Перезагрузить страницу (F5) тоже можно, но только после того, как сервис поднялся. Поручение
восстановится: его идентификатор страница помнит до закрытия вкладки. Автор проверял и более жёсткий
случай: полную пересборку и пересоздание контейнера (`docker compose stop`, `build app`, `up -d`).
Карточка вернулась и тогда.

### 7.8. Подтверждение и отправка

1. Нажмите «Отправить» в карточке. В карточке появится «Ваше решение: отправить.», затем шаги:
   - «Решение передано агенту» — «Агент продолжает с сохранённой контрольной точки.»;
   - «Инструмент вернул результат · send_telegram_message» — `Сообщение отправлено в 12345`;
   - «Ответ агента» — например, «Вы получите письмо об автопродлении за 3 дня до окончания периода.»;
   - зелёный шаг «Сообщение отправлено пользователю».
2. Справа: «Ждёт решения — нет», «Отправлено — да».
3. Проверьте лог сервиса:

```powershell
docker compose logs app --since 10m | Select-String TELEGRAM   # macOS, Linux: … | grep TELEGRAM
```

   Ожидаемо — ровно одна строка `[TELEGRAM → 12345] …`. Отправка — заглушка: настоящий Telegram API не
   вызывается, сообщение только пишется в лог.

### 7.9. Повторной отправки нет

Нажмите «Обновить состояние». Ожидаемо: «Это поручение уже выполнено: сообщение отправлено, повторной
отправки не будет.». Отправку защищают ключ идемпотентности и состояние в Postgres: даже повторный
`resume` через API второго сообщения не даст.

### 7.10. Отказ от отправки (по желанию)

1. Нажмите «Новое поручение»: появится новый идентификатор, шаги очистятся.
2. Нажмите «Выполнить» и дождитесь карточки, затем нажмите «Отклонить».
3. Ожидаемо:
   - в карточке — «Ваше решение: не отправлять.»;
   - результат инструмента — «Не отправлено: оператор отклонил отправку…»;
   - последний шаг — «Поручение завершено, сообщение не отправлено»;
   - справа — «Отправлено — нет».
   - Новой строки `[TELEGRAM → …]` в логе нет.

### 7.11. Новый документ в базе знаний

Вкладка «Пополнить базу». Ключ администратора должен быть задан.

1. Перетащите в рамку `samples/upload_tariffs_2027.pdf` из папки проекта или щёлкните по рамке и
   выберите файл. В рамке появится «upload_tariffs_2027.pdf · 68 КБ».
2. Нажмите «Добавить в базу». Статус меняется: «загружаю…» → «индексируется…» → «в базе · N с».
   - Если файл уже загружали, будет «в базе, без изменений».
   - Если загрузить файл с тем же именем, но другим содержимым — «в базе, новая версия».
   - У автора: «в базе, новая версия · 2 с». На свежем стенде — до 30–60 с.
3. Нажмите «Задать вопрос по документу», затем «Начать новый диалог». Спросите «Сколько стоит тариф
   «Квант» для студентов?».
4. Ответ: «Тариф «Квант» для студентов стоит 290 ₽ в месяц, с ограничением API на 30 запросов в
   минуту.». Справа `[1] upload_tariffs_2027.pdf` «в ответе», путь `uploads/upload_tariffs_2027.pdf ·
   uploads · стр. 1`, близость 0.81.

**Что это показывает:** документ, загруженный минуту назад, уже участвует в ответах. Сервис для этого не
перезапускался.

2. Выберите последний запрос `/chats/…/messages`. В дереве спанов видно, из каких шагов состоял ответ и

### 7.14. Тот же ассистент в Telegram (по желанию)

Нужен свой бот: впишите его токен от @BotFather в `BOT_TOKEN` в `.env` и выполните
`docker compose up -d bot`. Если Telegram API недоступен из вашей сети, задайте прокси в `BOT_PROXY_URL`
(см. [`bot.md`](bot.md)).

1. Задайте боту тот же вопрос, что в разделе 7.1: «Сколько действует ссылка для сброса пароля?». Ответ по
   существу тот же — 30 минут, а под ним «Источники:» с `account/password-reset.html`. Ответ строит

## 8. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| http://localhost:8000/ui — 404 | образ собран из версии без веб-интерфейса: `docker compose up -d --build` |
| Страница не открывается | `app` не поднялся: `docker compose ps`, `docker compose logs app --tail 30` |
| В шапке «сервис недоступен» | `app` перезапускается — подождите до минуты; `docker compose ps app` |
| `failed to connect to the docker API … dockerDesktopLinuxEngine` | Docker Desktop не запущен: запустите его, дождитесь «Engine running»; в `docker version` должен быть раздел `Server` |
| Docker Desktop: окно «WSL is unresponsive» или `500 Internal Server Error` от `docker compose` | завис WSL, обычно от нехватки памяти. Docker Desktop → Quit, затем `wsl --shutdown`, снова запустить Docker Desktop. Не помогло — перезагрузить компьютер |
| Ответ ждёт больше 90 с | модель загружается в память после запуска или простоя; см. `OLLAMA_KEEP_ALIVE` в разделе 3; `ollama ps` покажет загруженные модели |
| Ошибка `llm_unavailable` в ответе | контейнер не достучался до Ollama: запущена ли она (`ollama list`); на Linux — `OLLAMA_HOST=0.0.0.0` (раздел 3) |
| На вопросы из базы — «По базе не нашёл» с низкой близостью | индекс ещё строится: подождите строку `ingest_done` в `docker compose logs app` |
| «Ключ администратора не подошёл» | вставлен не тот ключ — скопируйте командой из раздела 6. После правки `.env` — `docker compose up -d app` |
| «Агент остановился с ошибкой» | нет модели агента или она не задана: `ollama list`, в `.env` — `AGENT__MODEL=qwen3:4b-instruct`, затем `docker compose up -d app` |
| 429 на вопрос | лимит 30 сообщений в минуту на пользователя — подождите минуту |
| Контейнер `bot` перезапускается | пуст `BOT_TOKEN` — для проверки в браузере бот не нужен: `docker compose stop bot` |
| `docker compose build` обрывается с EOF | не хватает памяти WSL: `docker compose stop`, затем `docker compose build app`, затем `docker compose up -d` |

## 10. Остановка

```powershell
docker compose stop               # данные остаются в томах: история, индекс, состояние агента, загрузки
```

`docker compose down -v` удалит и тома: при следующем запуске индекс построится заново (около минуты),
история чатов и загруженные документы пропадут.
